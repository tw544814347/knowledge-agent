# 非向量化方案

> **Page ID**: 2785041576
> **URL**: https://confluence.shopee.io/pages/viewpage.action?pageId=2785041576

传统的向量检索（Vector Search）将所有文档视为扁平的“语义浓汤”，擅长处理模糊和开放性问题。而以 RAPTOR 和 PageIndex 为代表的新方案，通过构建**知识的层级结构**（Hierarchy），实现了对信息更深层次的理解和更精确的导航，特别适合复杂和多维度的查询。这并非简单的“替代”关系，而是能力维度的扩展。

有大量结构复杂的长文档，且用户经常需要做归纳总结 -> 考虑RAPTOR/PageIndex

| 特性维度 | 传统向量方案 (Vector RAG) | 结构化/层级化方案 (e.g., RAPTOR, PageIndex) |
| --- | --- | --- |
| 核心隐喻 | “语义搅拌机” | “智能目录树” 或 “知识金字塔” |
| 工作原理 | 1. 将文档切分为固定或递归的文本块 (Chunks)。<br/>2. 将每个文本块独立编码为向量。<br/>3. 在一个扁平的向量空间中，通过相似度搜索找到最相关的文本块。 | RAPTOR (自下而上聚类):<br/>1. 先进行基础分块。<br/>2. 递归地对相似的块进行聚类，并用LLM生成上层摘要。<br/>3. 最终形成一个从具体细节到高度概括的树状结构。<br/><br/>PageIndex (自上而下索引):<br/>1. LLM先阅读全部文档，生成一个层级索引（像书的目录）。<br/>2. 用户的查询会先在这个“目录”上进行路由，找到最相关的“章节”。<br/>3. 最终定位到具体的叶子节点（原始文本块）。 |
| 检索方式 | 一步到位的相似度匹配 (Similarity Matching)。 | 多步导航式的查询路由 (Query Routing & Navigation)。 |
| 数据结构 | 扁平的列表 (Flat List of Chunks) | 树状/图状结构 (Tree/Graph Structure) |
| 优势 | - 实现简单，成熟稳定：生态成熟，开箱即用。<br/>- 擅长语义模糊搜索：能很好地处理同义词、近义词和开放性问题。<br/>- 召回率高：能找到大量可能相关的结果。 | - 理解上下文的广度与深度：能回答需要综合、归纳、总结多个文档片段才能回答的问题。<br/>- 检索精度高：通过层级导航，能精准定位到信息，减少不相关结果的干扰。<br/>- 减少“大海捞针”：避免了在数百万个扁平Chunks中进行暴力搜索。<br/>- 处理长文档能力强：天然地对长文档进行了结构化，解决了“Lost in the Middle”问题。 |
| 劣势 | - 上下文碎片化：严格的分块会破坏语义完整性（如表格、代码）。<br/>- 无法回答综合性问题：如果答案散落在多个不相邻的块中，很难被同时召回。<br/>- “中间迷失”问题：在长文本块中，中间的信息容易被忽略。<br/>- 精度不足：对于需要特定关键词或精确匹配的场景表现不佳。 | - 索引构建复杂且昂贵：无论是聚类摘要还是生成目录，都需要大量的LLM调用和计算资源，过程缓慢且成本高。<br/>- 对索引质量依赖高：如果LLM生成的摘要或目录质量差，会导致“一步错，步步错”，无法检索到正确内容。<br/>- 结构可能固化：PageIndex这类方案，如果查询方式与预设的目录结构不匹配，可能找不到答案。 |
| 最佳应用场景 | - 问答机器人 (FAQ Bot): 快速响应常见、独立的短问题。<br/>- 语义搜索：当用户不确定关键词时，进行模糊搜索。<br/>- 简单文档库的快速检索。 | - 研究与分析：“总结一下我们公司过去一年在AI项目上的所有投入和产出。” (需要跨多个报告进行归纳)。<br/>- 复杂文档库导航：在海量技术文档、法律文书中进行探索性查询。<br/>- 需要多层次抽象答案的场景。 |
