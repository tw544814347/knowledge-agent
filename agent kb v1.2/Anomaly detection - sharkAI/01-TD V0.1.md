主体流程
----

1. 通过近实时拉取监控平台的数据
2. 离线训练模型，生成模型文件
3. 模型服务加载训练好的模型文件
4. 检测服务通过监控平台获取的数据（或者附加其他数据源），访问模型服务获取异常检测评估结果。
5. 将异常检测评估结果（预测值，预测上下限，其他值）写回到监控平台

设计要点
----

1. 按需提供模型异常检测服务
   1. 初期不考虑全面铺开的方案（ROI也是一个考虑点）
   2. 后期和监控平台合作，提供接入开关供用户选择
   3. 迭代优化后，逐步接入更多业务
2. 主要针对周期性规律性指标提供数值预测服务
   1. 解决大部分有周期性规律指标的这部分告警配置问题
   2. 初期不求太全面，edge cases独立来看
   3. 不同曲线类型的支持逐步支持
3. 和公司监控平台打通
   1. 不单独搭建类TSDB，复用公司监控平台基建
   2. 尽可能复用监控平台能力，提供拓展能力
   3. 外部用户对接统一走公司监控平台
4. 使用业界成熟算法模型
   1. 优先使用业界通用成熟算法模型，匹配业务数据进行调优迭代
   2. 模型迭代优化是关键，需结合业务特性调优
5. 准确性提升逐步迭代
   1. 主要结合业务特性进行迭代

模块设计
====

数据ETL
-----

### 数据获取

ETL需求是从prometheus拉取数据，同步给模型训练，数据ETL功能主要有以下几点：

1、功能需求  
    1. 支持从prometheus数据源读取数据、写入目标存储介质  
    2. 支持通过promql拉取数据，支持动态发现新的promql  
    3. 数据读取保持有序  
    4. 支持实时读取有界/无界(时间范围)的prometheus数据  
    5. 保证读取数据的准确性、一致性、有序性  
    6. 容错和恢复  
    7. 负载均衡  
2、性能需求  
    1. 高吞吐  
    2. 低延迟

#### 方案一：利用flink调用prometheus的api接口获取数据

flink在处理实时数据上天然适合，并且考虑到容错恢复、数据准确性、高吞吐等需求，所以依赖flink实现数据etl是比较合适的选择。

flink提供了一系列底层接口，并且提供了流批一体的能力，底层的实现可以复用，基本框架如下

![iShot2024-07-23 17.49.42.png](https://confluence.shopee.io/download/attachments/2366363749/iShot2024-07-23%2017.49.42.png)

Enumerator和Reader是两个底层接口，Enumerator负责数据源分区的发现和分配，Reader负责数据的读取

介绍一下Prometheus Enumerator的分区发现以及分区分配怎么实现的

目前支持两种promql的配置方式，一种是用户在启动任务时初始化配置，另一种是用户配置动态发现分区的功能，通过Datos API读取参数配置，实现发动态发现promQl的功能。

动态分区发现变更后会通知Reader，Reader可能触发重分区，达到负载均衡的功能，目前仅支持hash分区。

![iShot2024-07-23 18.31.01.png](https://confluence.shopee.io/download/attachments/2366363749/iShot2024-07-23%2018.31.01.png)

flink数据读取流程如下：

当`KafkaSourceReader`接收到来自`KafkaSourceEnumerator`分配的Partition之后, 就会开始真正进行数据读取了. 数据读取的整体流程还是比较简单的, `KafkaSourceReader`运行在Task主线程中, 非阻塞地从`FutureCompletingBlockingQueue`中获取数据, 如果有数据就使用`KafkaRecordEmitter`向下游发送数据. `SplitFetcher`是真正的IO线程, 通过`KafkaPartitionSplitReader`从Kafka读取数据后放入`FutureCompletingBlockingQueue`

![image2024-7-24_11-46-4.png](https://confluence.shopee.io/download/attachments/2366363749/image2024-7-24_11-46-4.png)

在读取prometheus数据时，我们只需要注重fetch()方法的实现即可

下图中左侧是fetch()的实现流程，因为fetch()是周期性的被执行，所以在每次执行时不确定数据是否准备好，所以会设定一个定时器，在超时时间范围内，如果能够获取到数据则返回，超时未获取到数据则等待下次尝试。

如果在超时时间范围内，没有获取到数据，则会触发更新元数据的请求，更新元数据主要包括两个方面：

1、更新水位线，即prometheus最新的稳定数据，我们通过指标的采集时间来确定水位线，目前设计方案是：**指标最新时间戳-允许的延迟时间**

2、可以拉取的时间范围

解释：我们采取多线程异步请求的方式拉取数据，为了保证数据有序以及较高的吞吐量，一个flink task可能同时拉取多个时间区间(1分钟)的数据，数据采集到之后会暂存在优先级队列中。这个可以拉取的时间区间需要不断更新，限制条件是：时间戳<=水位线 && 时间戳>已处理的最新时间戳 && 时间区间的个数 <= 一个task同时能能处理的最大请求数(已经封装好的请求 + 正在发送的请求)

下图右侧是poll()方法的具体流程，首先解释一下，这里使用PriorityQueue来存放数据，通过优先级队列实现数据的异步存取。

从队列获取数据时

1、如果未获取到数据，则准备重新发送请求拉取数据。

2、如果数据是有效数据，即元数据中存储的下一个待处理的时间戳和当前数据的时间戳一致，那么直接返回该数据。

3、如果从队列中获取的数据是无效数据时，数据时间戳小于元数据中存储的下一个待处理的时间戳，则判断数据是处理过的，直接丢弃。

4、如果从队列中获取的数据是无效数据时， 数据时间戳大于元数据中存储的下一个待处理的时间戳，判断数据不是下一个待处理的数据，表示此时数据存在乱序，将重新发送请求(下一个时间区间的请求)，并将无效数据放回队列。

拉取数据时

1、首先准备可以发送的数据请求

2、发送请求至请求队列，等待异步执行

3、请求返回后，执行异步回调方法，数据如果成功返回，则写入优先级队列，如果请求异常，则等待重试

![image2024-9-13_18-1-48.png](https://confluence.shopee.io/download/attachments/2366363749/image2024-9-13_18-1-48.png)

配置数据源：

目前从公司监控平台拉取prometheus数据，至少需要提供Query URL和拉取数据的promQL

1.Query URL是与MetricStore绑定的，一般不同的组织/项目会申请不同的MetricStore，所以考虑到扩展性，我们需要获取到使用方Query URL

2.使用方的promQL可能是多样性的，比如5分钟内各个function的请求量、5分钟内各个function的请求量增加比例

-- 简单统计
sum(avg\_over\_time(metric\_gauge\_kfk\_biz\_less\_threshold\_cnt{job="biz-data-latency"}[5m])) by (region,topic\_name)
-- 逻辑运算
sum(avg\_over\_time(metric\_gauge\_kfk\_biz\_greate\_threshold\_cnt{ job="biz-data-latency", topic\_name!~ ".\*live\_dwd\_request\_log.\*"}[5m])) by (region,topic\_name) / (sum(avg\_over\_time(metric\_gauge\_kfk\_biz\_greate\_threshold\_cnt{ job="biz-data-latency", topic\_name!~ ".\*live\_dwd\_request\_log.\*"}[5m])) by (region,topic\_name) + sum(avg\_over\_time(metric\_gauge\_kfk\_biz\_less\_threshold\_cnt{ job="biz-data-latency", topic\_name!~ ".\*live\_dwd\_request\_log.\*"}[5m])) by (region,topic\_name)) and sum(avg\_over\_time(metric\_gauge\_kfk\_biz\_greate\_threshold\_cnt{ job="biz-data-latency", topic\_name!~ ".\*live\_dwd\_request\_log.\*"}[5m])) by (region,topic\_name) > 100

* 对于比例/环比/同比的指标，暂时不考虑（可以考虑对于复合运算拆成独立指标）。
* 由于监控是非实时的，所以获取数据的周期至少是分钟级别。

### 数据回写

构建prometheus指标

通过antlr解析用户的promql，获取用户by的标签，同时会写入promql\_name，metricstore\_name

1.定义5个指标并重构label

系统构建默认标签：

* job = "shark-monitor"
* detect\_metric\_store = "${metricstore\_name}"
* detect\_yhat\_name = "${promql\_name}"

2.通过antlr解析promql，获取用户需要回写的标签（by 字段），把查询的结果数据填入标签值

| metric | 描述 | 例子 |
| --- | --- | --- |
| detect\_y | 业务上报原始指标 | detect\_y{job="shark-monitor", ...} |
| detect\_yhat\_future | 业务指标未来预测值 | detect\_yhat\_future{job="shark-monitor", ...} |
| detect\_yhat\_future\_lower | 业务指标未来上限值 | detect\_yhat\_future\_lower{job="shark-monitor", ...} |
| detect\_yhat\_future\_upper | 业务指标未来下限值 | detect\_yhat\_future\_upper{job="shark-monitor", ...} |

3.数据回写到原来prometheus

由于要写入预测数据（带有时间戳），在此使用influxdb协议写入数据
