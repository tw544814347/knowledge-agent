一、AI Agent基础与Smart平台概览
======================

agent 相关概念介绍
------------

Agent（智能体） 是指能够感知环境、进行决策并执行动作以实现特定目标的实体。

一个典型的 Agent 通常包含以下核心要素：

* **感知**：接收来自环境的信息（如用户输入、API 返回等）。
* **思考/决策**：基于内部知识、大语言模型（LLM）推理或规则，决定下一步行动。
* **行动**：调用工具、生成回复、更新状态等，对环境产生影响。

![image2026-3-18_16-4-18.png](https://confluence.shopee.io/download/attachments/3134098619/image2026-3-18_16-4-18.png)

| 概念 | 简要定义 | 在Agent中的角色 | 示例/说明 |
| --- | --- | --- | --- |
| **LLM** | 大型语言模型（如GPT-4、Claude），擅长文本理解与生成 | 作为Agent的“大脑”，负责意图理解、推理规划、自然语言响应 | “用GPT-4驱动一个客服Agent，回答用户问题” |
| **ReAct** | 推理（Reason）与行动（Act）交替协同的工作范式 | 让Agent边思考边执行，并根据环境反馈调整下一步行动 | 思考“用户想查天气”→调用天气API→观察结果→告知用户 |
| **Skill** | 将专业领域的工作流程、规范与配套工具打包成的一个文件夹（包含[SKILL.md](http://SKILL.md)说明文档、脚本等） | 为Agent提供“岗位说明书+专家工具箱”，使其在特定场景下按专业规范自主执行，且按需加载、不占上下文 | 一个“财务合规审查Skill”：Agent遇到相关需求时自动加载SKILL.md，按步骤调取数据、比对规则、生成报告 |
| **MCP Server** | 模型上下文协议（Model Context Protocol）  通过标准化接口向LLM提供工具、资源和提示 | 作为Agent能力的“可插拔插件”，使LLM能动态发现并调用任意MCP协议兼容的工具 | 本地启动一个MCP Server连接数据库，Claude Desktop直接询问“上季度销售额”，Server自动映射成SQL查询 |
| **Tool** | 可被Agent调用的外部函数或API | 赋予Agent执行具体操作的能力，突破LLM自身限制 | 计算器工具、航班查询API、发送邮件的函数 |
| **Function Calling** | LLM以结构化JSON格式输出函数名称及参数，请求调用预设函数 | 将用户意图精准映射到工具参数，是Tool落地的主流实现方式 | 用户：“给张三发邮件”，模型输出`send_email(to: \"zhangsan@xx.com\", subject: \"...\")` |
| **Knowledge** | 以结构化或非结构化形式存储的领域信息、规则、经验或实体关系 | 为Agent提供长期记忆和背景知识，支撑推理决策 | 企业内部规章制度、产品技术文档、医学知识图谱、客户历史交互记录 |
| **Memory** | Agent对对话历史、状态信息或长期知识的存储与管理能力 | 维持对话连贯性，实现状态跟踪、跨会话记忆 | 短期：对话窗口中的上下文；长期：向量数据库存储用户偏好 |

Agent 常见模式

| 模式 | 核心思想 | 特点 | 适用场景 |
| --- | --- | --- | --- |
| **Single-Agent** | 单个智能体独立完成所有任务，拥有完整的工具集、记忆和规划能力。 | - 架构简单，开发调试容易 - 扩展性有限，难以处理需要多角色协作的复杂任务 | - 简单问答（如客服机器人） - 单一领域任务（如个人日程助理） |
| **Multi-Agent** | 多个专业智能体协同工作，每个有独立角色、目标和工具，通过通信完成整体任务。 | - 模块化、可扩展，各 Agent 可专注特定领域 - 黑盒决策，可控性低 | - 复杂业务流程（如旅行规划：机票、酒店、景点各自负责） - 多角色交互模拟（如虚拟团队协作） |
| **Workflow** | 将任务流程预定义为有向无环图（DAG），节点可以是 Agent、工具或逻辑判断，数据按边流转。 | - 流程可控、确定性高 - 灵活性较低，难以应对动态变化的需求 | - 固定流程任务（如数据清洗流水线） |

**Multi-Agent**

| 模式 | 核心思想 | 工作流程 | 适用场景 | 优点 | 缺点 | 典型示例 |
| --- | --- | --- | --- | --- | --- | --- |
| **转交模式 (Handoff)** | 当前Agent将对话上下文和控制权完全移交给另一个更合适的Agent，原Agent退出。 | 1. Agent A 处理任务，发现需要专业知识 2. Agent A 触发转交，将完整上下文传给Agent B 3. Agent B 接管后续对话 | - 客服升级（一线→二线） - 多轮对话中领域切换（如从天气查询转到机票预订） - 需要保持上下文连续性的场景 | - 上下文无缝衔接，用户体验好 - 各Agent职责专注，无需全局协调 | - 转交逻辑复杂，需防止循环转交 - 原Agent退出后无法回溯 | 客服机器人：用户询问订单问题，转交给订单专员Agent；专员完成后，对话结束。 |
| **嵌套模式 (Nested)** | 一个Agent在任务执行过程中动态调用另一个Agent作为子任务执行器，子Agent返回结果后父Agent继续处理。 | 1. 父Agent接到复杂任务，拆分为子任务 2. 父Agent调用子Agent（可多次），传入必要参数 3. 子Agent独立执行，返回结果 4. 父Agent整合结果，继续推进主任务 | - 复杂任务分解（如旅行规划：主Agent调用机票、酒店子Agent） - 需要复用专业能力（如主Agent调用代码生成Agent） - 类似编程中的函数调用 | - 模块化，子Agent可复用 - 父Agent保持全局控制，流程清晰 | - 深度嵌套可能导致响应延迟 - 需设计父子通信协议 | 研究助手：主Agent收到问题“分析某公司财报”，调用“财报提取Agent”获取数据，再调用“财务分析Agent”生成报告，最后整合输出。 |
| **主代理模式 (Master)** | 一个主控Agent负责任务分解、调度、协调和汇总，工作Agent之间可能需要相互通信交换中间结果。 | 1. 主控Agent分析任务，生成计划 2. 主控分配子任务给多个工作Agent，并告知它们可能需要的协作关系 3. 工作Agent执行任务，必要时直接与其他工作Agent交换信息 4. 工作Agent将结果返回主控，主控整合后输出 | - 复杂协作任务（如软件开发：设计、编码、测试Agent协同） - 需要多Agent信息交换的场景（如旅行规划需协调机票、酒店、景点） | - 全局最优，主控可动态调整计划 - 适合需要深度协作的复杂流程 | - 主控可能成为瓶颈 - 通信开销大，需设计协作协议 | 软件开发团队：主控（项目经理Agent）拆解需求，分配编码Agent、测试Agent，二者可交互代码和测试用例，最后主控汇总交付。 |
| **群聊模式 (Group Chat)** | 多个Agent在共享对话环境中自由交流，平等参与，通过自然语言讨论达成共识或产生输出。 | 1. 所有Agent加入同一个“聊天室” 2. 用户输入或某个Agent发起话题 3. Agent们轮流发言（或并行），相互评论、补充、反驳 4. 经过多轮讨论，产生最终结论或行动 | - 头脑风暴、创意生成 - 多角色模拟（如法庭辩论、投资决策委员会） - 需要聚合多方观点的场景 | - 高度灵活，模拟真实人类团队协作 - 能产生集体智慧，可能超出单个Agent能力 | - 难以控制收敛，可能出现冗长讨论 - 需设计发言顺序和终止条件 | 投资委员会：多个Agent扮演不同角色（技术分析、基本面分析、风控），讨论某股票是否值得投资，最终形成投资建议。 |

**Workflow**

Workflow 模式由Node和Variable组成，可以想象成工厂流水线：

● Nodes 是独立的工作站，每个工作站执行一个明确的步骤。

● Variables 是流水线中待加工的“盒子”。由Node加工后放回到流水线中，直到流程结束。

Smart 介绍
--------

[Smart(Sea Multi-Agent Realisation Technology)](https://smart.shopee.io/) 是 Sea 内部自研的 AI 智能体平台。它旨在帮助团队快速构建、调试、部署和扩展基于大语言模型（LLM）的 AI 智能体，为各类业务场景提供一站式的智能解决方案。

Smart 平台的核心设计理念是灵活性与生产级可靠性的统一：

* **架构支持**：原生支持 **Single-Agent（单智能体）**、**Multi-Agent（多智能体）** 和 **Workflow（工作流）** 三种主流 AI 架构，覆盖从简单对话到复杂协作的全场景需求。
* **无缝集成**：提供tools、knowledge bases以及端到端业务工作流的标准化接入能力，让智能体能够真正融入实际业务流程。
* **全生命周期管理**：从快速原型验证到生产级关键任务系统，Smart 提供一致的开发体验和强大的运维支撑。

2.1 CURSOR辅助业务知识梳理
------------------

由于缺乏对业务系统的深入了解，开发过程中遇到的一些问题往往会困扰我们：

* 页面与表之间的对应关系；
* 数据库表的具体作用；
* 表中字段的业务含义；
* 字段枚举值；
* 表与表之间的关联关系。

在SSC Mart重构项目的前期阶段，开展了全面的业务梳理工作，旨在深入理解现有业务系统的功能模块、接口设计、数据表字段定义及表间关联关系，为后续模型设计奠定清晰、准确的基础。

以SPX系统为例，其涵盖8个业务域。FMS系统上每个业务域平均包含约 25 个页面、上百个接口与数据表，上千字段。若完全依赖人工方式进行梳理，工作量极为庞大，且效率低下。

因此探索了一套借用cursor的业务梳理方法论，辅助业务知识的梳理。

**核心梳理流程**

1. 梳理系统页面功能，初步了解系统模块与功能。（人工）
2. 梳理页面接口，了解清楚每个页面背后查询了哪些表，这些表的关联关系是怎样的。（日志检索+Cursor+人工）
3. 深入梳理与探查表字段，了解清楚每个字段的含义、生成逻辑、枚举等信息。（Cursor+spark脚本+人工）

![image2025-12-22_14-55-32.png](https://confluence.shopee.io/download/attachments/3134098619/image2025-12-22_14-55-32.png)

**简要说明**：

| 步骤 | 核心任务 | 主要工具 | 输出产物 |
| --- | --- | --- | --- |
| **Step 1** | 获取页面与接口映射 | Grafana APM平台 | 页面URL → API列表 |
| **Step 2** | 获取接口与表映射 | Cat监控平台 | API → 数据库表列表 |
| **Step 3** | cursor页面梳理 | Cursor | 页面接口功能描述 |
| **Step 4** | 拉取表明细 | SQL查询 | 表结构（字段、类型、约束等） |
| **Step 5** | cursor表字段梳理 | Cursor | 字段含义、生产枚举值、生成逻辑等 |
| **Step 6** | 表字段探查 | Notebook脚本 | 表数据情况（枚举分布、缺失情况等） |

2.3 Trouble Shooting
--------------------

每卖出一份保险，保险公司需要向我们支付一笔佣金（commission）。

这个值是由PM配置规则，由DE计算的，记录在 policy\\_tab 的 commission 字段。

计算 commission 过程中的一些问题可能导致结果为 null 或 负数，比如：

1.有时候新保险已经开售了，但PM还没配置commission计算规则。

2.BE版本迭代或新增了一些规则过滤逻辑，但 这边commission 加工逻辑没适配。

3. 线上原有计算逻辑的问题。

commission 由 processor sql 计算

pi每个市场有**5～7个processor** ，且目前没有模板化

每个processor 的计算逻辑有**200 ～ 300 行**，涉及的**表多**，**关联多**。

检查的时候需要**逐步排查**，**过程比较繁琐。**

![image2026-3-18_9-33-16.png](https://confluence.shopee.io/download/attachments/3134098619/image2026-3-18_9-33-16.png)

![image2026-3-18_14-50-55.png](https://confluence.shopee.io/download/attachments/3134098619/image2026-3-18_14-50-55.png)

2.4 告警总结分析
----------

原本处理告警的pipeline

1.看监控：发现接口报警，拿到错误码。

2.查定义：去公司内部的错误码管理平台，查这个码属于哪个模块，具体含义是什么（是配置错还是代码挂）。

3.找链路：去日志系统里捞一条报错的请求，找到调用链路，提取出一个关键的 msgno 串。

4.上机器拉异常堆栈文本。

5.看懂堆栈，定位原因，修改代码。

将上面的SOP拆解成Agent的workflow。

通过创建tool给Agent提供日志、源码、错误码信息。

利用LLM的推理能力，分析错误原因。

三、一些感受
======

**1.从关注“怎么写”到关注“怎么问”：提问的质量，决定了AI输出的上限。**需要学会精准表达需求。

**2.从亲力亲为到指挥若定：Coder → Director**：角色从自己干的执行者，进化为教AI干的总指挥。

**3.SOP + 知识 + AI = 提效利器**：将隐性经验固化为标准流程，叠加AI的执行力，实现效率的提升。

**4.从“单点解决”到“批量复制”**：过去解决一个问题就是一个点；现在沉淀出一个SOP，就能让AI批量处理一类问题，实现能力的快速复制。
